02 / Problem Space

Brands had the intent. They lacked the tools to act on it.

Before Club Dashboard, brands managed ambassador programs through disconnected spreadsheets, manual Slack threads, and generic SaaS tools that weren't built for gamified engagement. The result: high-potential campaigns were limited by operational friction rather than strategy.

Business Problems

No Performance Visibility

Brands couldn't measure ROI on ambassador activity. Campaign performance was a black box — they saw cost, not impact.

Passive Ambassador Base

Without structured missions, ambassadors self-organized inconsistently. Brands couldn't drive specific behaviors or measure which actions correlated with revenue.

Slow Campaign Iteration

Modifying a campaign required developer involvement. Brands waited days to change a mission description or adjust a reward — killing responsiveness to market feedback.

Fragmented Tooling

Brands juggled 4–6 tools for what should be a unified workflow: mission planning in Notion, user lists in Sheets, comms in Slack, analytics in Looker — none of it connected.

Admin (User) Problems

Complex Mission Creation

Creating a mission involved too many decisions at once — type, reward, proof, audience, timing — without clear guidance on what good configuration looks like.

Unclear Insights

Raw data was available, but it wasn't actionable. Admins saw numbers — not answers. "What should I do next?" was never answered by the analytics layer.

User Management Blind Spots

Admins couldn't identify high-value ambassadors, at-risk churners, or segmented cohorts without exporting data to external tools first.

No Optimization Workflow

When a mission underperformed, there was no guided path to diagnose why or fix it. Admins edited blindly, hoping something would improve completion rates.

The biggest barrier wasn't brand commitment — it was operational friction. Brands that wanted to run great campaigns were stuck fighting their tools instead of serving their ambassadors.

Synthesized from 18 brand admin interviews, stakeholder sessions, and support ticket analysis — Q2 2023

Goals & Constraints

Design Goals
  • Reduce mission creation time from 23 min avg to under 10 min
  • Surface actionable insights — not just data
  • Enable brands to run and iterate campaigns without dev involvement
  • Give user management enough depth to identify high-value segments
  • Create a scalable system that supports 100+ brands without UI complexity
Constraints
  • Existing event pipeline and data schema — we couldn't redesign the backend
  • Analytics refresh rate: every 4 hours — real-time wasn't possible at MVP
  • No white-labeling in MVP — single dashboard skin for all brands
  • Manual mission review for proof-based types — no auto-AI validation yet
  • MVP scope: Club creation, Mission builder, Analytics, User management

03 / Product Thinking

The dashboard is the flywheel — it determines everything downstream

The Club ecosystem is a feedback loop system. The dashboard is where that loop gets configured, measured, and improved. Every decision a brand makes in the dashboard directly shapes the experience millions of ambassadors have in the app.

Step 01
Create

Brand admin creates a Club, defines Missions, configures rewards and entry criteria. The system is configured — nothing moves until this is done.

→
Step 02
Engage

Ambassadors discover the Club in the app, complete Missions, and earn Coins. Real-world behaviors — purchases, reviews, referrals — are executed and logged.

→
Step 03
Measure

Every action generates data: completion rates, drop-off points, cohort behavior, coin distribution, ROI attribution. The dashboard surfaces this as insight.

→
Step 04
Optimize

Brand admin reviews performance, identifies underperforming missions, adjusts rewards or requirements — and publishes improvements. The loop closes and repeats.

Why the system view matters

Most dashboard products treat each feature as independent. The mission builder is "the mission builder." Analytics is "the analytics page." We designed each module as a node in the feedback loop — decisions made in one feature ripple through the rest.

Configuration → Behavior

The quality of a mission config directly predicts its completion rate. We designed the builder to guide admins toward high-performing patterns, not just allow arbitrary configuration.

Data → Action

Every data point in the analytics layer is connected to an action. When completion rate drops below threshold, the system surfaces the exact mission and suggests next steps — not just a number.

Iteration → Improvement

The system preserves campaign history. Every edit to a mission creates a version. Admins see trend lines, not snapshots — so improvements are visible and attributable.

Flow 01

Create a Club

Brand admin creates a new goal-based community for their ambassadors. Entry point: Clubs section → Create Club button.

01
Navigate to Clubs section

Admin selects "Clubs" from the primary sidebar. If this is the first club for the brand, an empty state is displayed: illustration + headline "You haven't created any clubs yet" + CTA button "Create your first club". If clubs exist, a list/grid of club cards is shown with status badges (Active, Draft, Paused) and quick stats (member count, active missions, completion rate).

○ Empty state: Shown on first visit. Includes a brief explainer of what clubs are, so new admins understand the concept before creating one.
02
Click "Create Club"

A right-side panel slides in (or a full-page form opens) — the Club Builder. It is divided into 3 clear sections: Identity, Criteria, Goals. A progress indicator at the top shows which section is active. The header always shows a live preview of the club card as it will appear in the app — changes reflect in real time.

03
Section 1 — Club Identity

Admin fills in: Club name (required), Tagline / short description (max 120 chars), Cover image (upload or pick from brand library), Brand accent color (hex picker or presets from brand kit). Character limits shown inline. Live preview updates with each change. Tooltip hints for best practices: "Clubs with a photo get 2.3× more joins."

04
Section 2 — Entry Criteria

Admin selects how users can join: Open to all (any ambassador can join), Invite only (admin sends invites, or users request to join), or Level-gated (only ambassadors at or above a certain Club level). If Level-gated: a dropdown appears to set the minimum level (1–5). A note explains the tradeoff: "Open clubs grow faster. Gated clubs drive higher engagement per member."

05
Section 3 — Club Goal (optional)

Admin can optionally define a campaign goal: total missions to complete, engagement score target, or revenue attribution target. This goal is used in the analytics layer to show progress-toward-goal charts. If no goal is set, analytics defaults to "no target set" state — always accessible but never blocking.

06
Review & Preview

Admin sees a side-by-side: the raw form data on the left, and the exact club card + detail screen (as it will look in the app) on the right. A checklist at the bottom shows: "Add a cover image ✓ | Set entry criteria ✓ | Add at least one mission before publishing ⚠". The mission warning is advisory — publishing a club with no missions is allowed but not recommended.

⬟
Decision: Publish or Save Draft?
Publish

Club goes live immediately. Visible to ambassadors in the Club App's discovery feed. Analytics baseline initialized. Admin redirected to Club detail page.

Save Draft

Club saved with Draft status. Not visible to users. Admin can continue editing at any time. Drafts appear in the Clubs list with a "Draft" status badge.

System: Club Published Successfully

Toast notification: "Club published. Ambassadors can now discover and join." Club detail page loads showing: 0 members, empty mission list with CTA "Add your first mission", analytics section showing "Awaiting first activity." Onboarding checklist appears in the right panel to guide next steps.

Error State: Validation Failed

If Club name is missing or entry criteria not selected: fields highlighted in red with inline error messages. Form does not submit. Admin is not navigated away — they fix the field and try again. No data is lost.

Flow 02

Create a Mission

Brand admin builds a new mission — a discrete, completable task that drives a specific brand behavior. Entry points: Missions section → Add Mission, or Club detail → Add Mission.

01
Open the Mission Builder

The Mission Builder opens in a dedicated full-width view (not a modal — mission creation is complex enough to warrant its own context). The builder is split into a left-side form and a right-side live preview of the mission card as it will appear to ambassadors. A horizontal stepper at the top shows: Type → Details → Requirements → Reward → Availability → Review.

02
Step 1 — Select Mission Type

Admin selects a mission type from 6 options. Each type is shown as a card with icon, label, example use case, and typical coin range. Types: Purchase, Social Share, Review, Referral, Survey, Check-in. Hovering a type shows a tooltip with "Completion rate avg: X%" based on platform-wide data. The selected type determines which requirement fields appear in Step 3.

03
Step 2 — Mission Details

Admin fills in: Mission title (required, max 60 chars), Description / what to do (required, max 400 chars, rich text), Instructions / how to complete (optional, markdown supported), Hero image (optional, shown at top of mission detail in the app). Character counters shown. Placeholder hints use actual examples: "e.g., Share a photo of your purchase on Instagram with #[brand]".

04
Step 3 — Requirements

Fields vary by mission type. Common fields: Proof type (photo upload / URL / order number / automatic via Klaviyo event), Verification method (automatic / manual brand review), Minimum threshold (e.g., "Purchase must be ≥ $25"). For Social missions: hashtag required, optional platform filter (Instagram / TikTok / X). Manual review missions show: estimated review time field (used to set user expectations in the app).

⚠ Validation warning: If manual review is selected but no review time is set, a warning appears: "Add an estimated review time so ambassadors know what to expect." Not blocking, but prominently shown.
05
Step 4 — Reward Configuration

Admin sets the coin reward value using a slider (10–2000 coins) with manual input fallback. A recommendation band is shown: "Typical for this mission type: 100–300 coins." Below the slider, an optional multiplier section allows higher coin rates for specific ambassador levels (e.g., "Champions earn 1.5× for this mission"). Projected cost estimate shown: "At current engagement levels, this mission may distribute ~X coins total."

06
Step 5 — Availability

Admin configures: Start date (required, defaults to now), End date (optional — missions without end dates run indefinitely), Max completions (unlimited / cap at X — useful for limited-time reward budgets). Audience rules: assign to specific Club(s) or make available across all clubs. An urgency toggle adds a countdown timer visible to users (automatically activates when ≤72 hours remain to deadline).

07
Step 6 — Review Summary

Full mission summary displayed: all configured fields in read-only format, the app preview card on the right, and a pre-publish checklist. Checklist items: "Mission type selected ✓ | Instructions clear ✓ | Coin value set ✓ | At least one club assigned ✓". Admin can jump back to any section by clicking the stepper or an inline "Edit" link next to each summary block.

⬟
Decision: Publish or Save Draft?
Publish

Mission goes live to all eligible ambassadors in assigned clubs. Status badge = "Active." Performance tracking begins immediately.

Save Draft

Mission saved with "Draft" status. Not visible to users. Can be edited and published at any time. Draft count badge visible on Missions nav item.

System: Mission Published

Toast: "Mission live. Ambassadors in [Club Name] can now see it." Admin is redirected to the mission detail page. Initial state: 0 views, 0 starts, 0 completions. A note explains: "Performance data will appear here once ambassadors interact with this mission."

Error States

Coin value missing: Field highlighted, stepper shows error indicator on Step 4. End date before start date: Inline date error. No club assigned: Warning in Step 5 + pre-publish checklist shows unchecked. Large reward alert: If coin value is set to 5× above the type's average, a confirmation dialog appears: "This reward is significantly higher than average. Confirm?"

Flow 03

Track Performance

Brand admin reviews campaign analytics to understand what's working and what needs attention. Entry point: Analytics section from main nav.

01
Navigate to Analytics Overview

Analytics section loads. Top-level KPI row shows: Total Members (all clubs), Active This Week (users who completed ≥1 mission), Missions Completed (total), Coins Distributed, and Campaign ROI Estimate. KPIs have a ±% change indicator vs. the previous period. A banner shows the last analytics refresh timestamp with countdown to next refresh (every 4 hours).

○ Empty state: New accounts see "Your analytics will appear here once you have at least 10 ambassador interactions." Motivates them to publish missions and drive activity.
02
Select Time Range

Admin applies a time filter: presets (Last 7 days / 30 days / 90 days / This month / Custom). Custom range opens a calendar date picker. All KPIs and charts update immediately to reflect the selected range. The period comparison always shows vs. the equivalent prior period (e.g., 30-day view compares to the 30 days before that). Custom ranges show "Compared to equivalent prior period" in a tooltip.

03
View Club-Level Breakdown

Below the top-level KPIs, a Club Performance table lists all active clubs. Columns: Club name, Members, Active Rate (%), Missions Completed, Avg Completion Time, Top Mission. Sortable by any column. Color-coded performance bands: green (above 60% active rate), amber (30–60%), red (below 30%). Admin clicks a club row to drill into club-specific analytics.

04
Drill Into Club Analytics

Club analytics view shows: member growth chart (joined vs. churned per week), mission completion funnel, top 5 ambassadors by coins earned, level distribution chart. Mission Performance table shows all missions for this club with: views, start rate, completion rate, approval rate (for manual missions), coins distributed. Table rows are clickable — each leads to individual mission analytics.

05
Filter by Segment

Admin applies user segment filters to scope analytics: by ambassador Level (1–5), Join Date Cohort (joined this month / last month / 3+ months ago), Activity Status (Active / At-Risk / Churned). Filters stack — admin can view "Level 3+ ambassadors who joined last month and are at risk." Filtered analytics help identify specific cohort problems before they affect the overall numbers.

06
Export Report

Admin clicks "Export" in the top-right. Options: CSV (raw event data) or PDF (formatted summary report). PDF includes the current filters, time range, KPI summary, club table, and top insights. Generation takes 5–15 seconds — a progress indicator is shown. On completion: "Report ready" toast with download link that expires in 24 hours.

System: Insight Surfaced

When the analytics engine detects a significant pattern (mission below 25% completion, user churn spike, engagement drop vs. previous period), a contextual Insight card appears at the top of the relevant section: "3 missions are underperforming. Review and optimize →". These insights are not alerts — they're contextual, not modal, and always linked to an action.

Flow 04

Manage Users

Brand admin views, filters, and takes action on their ambassador base. Entry point: Members section from main nav.

01
View Ambassador List

Members section shows a sortable data table: columns include Avatar, Name/Email, Club Membership, Level, Missions Completed, Coins Earned, Last Active, Status (Active / At-Risk / Churned). Defaults sort: Last Active descending. Color-coded status badge helps admins spot disengaging users at a glance. Pagination at 50 rows per page.

○ Empty state: "No ambassadors yet. Once users join your clubs, they'll appear here." Includes a link to the Club Invite feature.
02
Filter and Search

Filter bar above the table: search by name or email (debounced, 300ms), filter by Club (multi-select dropdown), Level (1–5 checkboxes), Status (Active / At-Risk / Churned), Tags (custom label filter). Filters stack and combine. Active filter count shown in badge. One-click "Clear all filters" resets to default view. Applied filters persist in URL params — shareable.

03
Open User Profile

Admin clicks a user row → a right-side profile drawer slides open (the main table remains visible and scrollable). Drawer contains: user avatar + name, member since, current level across each club, coins earned (total + by club), missions completed (with status breakdown: approved / pending / rejected), and an activity timeline showing the last 30 events.

04
Review Activity Timeline

Timeline entries include: "Joined Club [X]", "Completed mission [Y] — earned 200 coins", "Mission [Z] — proof under review", "Reached Level 3 in [Club]", "Redeemed reward: $10 gift card". Entries are timestamped and filterable by type. Admins can click a mission entry to jump directly to that mission's detail page.

05
Take Actions on User

Action buttons in the profile drawer: "Assign Tag" (add custom label like "VIP", "High Value", "Review Needed"), "Adjust Level" (manual override with required reason field — "Override: Manual adjustment by admin [date]"), "Send Notification" (send a custom push notification to this user), and "View Full Profile" (opens dedicated user profile page with full history).

⬟
Decision: Suspend Account?
Suspend

Confirmation dialog: "Suspend [User Name]? They will be unable to complete missions or earn coins until reinstated." Requires reason field. User sees "Account suspended" in the app.

No Action

Dismiss dialog. No changes to user account. Profile drawer remains open for further review.

System: Action Confirmed

Tag assigned: Toast "Tag 'VIP Ambassador' applied to [Name]." Level adjusted: Toast "Level updated. This override will appear in [Name]'s activity log." Suspension: Toast "Account suspended. [Name] cannot access missions until reinstated." All actions are reversible and logged in the user's audit trail.

Flow 05

Optimize Campaign

Brand admin identifies underperforming missions, diagnoses the cause, and iterates to improve completion rates. Entry point: Analytics → Mission Performance, or an in-dashboard Insight card.

01
Identify Underperforming Missions

Analytics → Mission Performance view shows a sortable table of all active missions with completion rates. Missions below the platform threshold (25% completion) are flagged with an amber warning badge. If the system has detected a significant drop from a mission's own historical baseline, a "Trending down" indicator is also shown. Admin can sort by completion rate ascending to prioritize the worst performers.

02
Open Mission Funnel

Admin clicks a mission row → Mission Funnel detail view opens. The funnel shows step-by-step drop-off: Visible to eligible users → Viewed mission detail → Started mission → Submitted proof → Approved. Each step shows absolute count and % conversion from the previous step. The biggest drop-off point is highlighted with a red ring and label: "68% of users who start this mission abandon at proof submission."

03
Read System Insight

Below the funnel, a contextual Insight card displays a system-generated suggestion based on the drop-off pattern: "Most users abandon this mission at proof submission. Consider simplifying the proof requirement or adding example images to the instructions." The insight is deterministic — it reads from a predefined set of patterns (proof drop-off, start rate drop, approval rate low) rather than ML inference, ensuring reliability at MVP scale.

04
Click "Optimize Mission"

Admin clicks the "Optimize Mission" CTA in the insight card (or "Edit Mission" from the mission detail header). The Mission Builder reopens with all current fields pre-populated. A change summary panel on the right shows: "You are editing a live mission. Changes will apply to all ambassadors who have not yet started it." In-progress submissions are not affected.

⬟
Decision: What to change?
Edit Content

Simplify instructions, clarify proof requirements, add example images. For proof drop-off: change proof type from "photo + order number" to "photo only."

Adjust Reward or Deadline

Increase coin value to drive more starts, extend the deadline to reduce urgency pressure, or cap completions to create scarcity. Each change has a projected impact note.

06
Save Changes → Version Created

Admin saves changes. The mission's version history is updated: "Version 2 — [Date] — Edited by [Admin]. Changed proof type from 'photo + order number' to 'photo only'. Changed description." Previous version preserved for rollback. A confirmation banner: "Changes saved. Updated mission is now live."

⚠ Large reward alert: If coin value is increased by more than 2× the original, a confirmation dialog: "This significantly increases reward value. At current engagement levels, this may distribute ~X additional coins. Confirm?"
System: Impact Tracked

The mission analytics page now shows a version change marker on the completion rate trend chart — a vertical dotted line labeled "v2 published." This allows the admin to visually attribute any subsequent improvement (or decline) to the specific change. After the next analytics refresh (4 hours), the before/after completion rate comparison is shown. If rate improves by ≥10pp, a "Optimization successful" badge appears on the mission card.

06 / Key Features

Five modules. One connected admin experience.

Each module solves a specific operational problem for brand admins. Together, they form a complete campaign management system that replaces the 4–6 disconnected tools brands previously used.

Club Management

Campaign Container

Clubs are the top-level containers for brand campaigns. Each Club has its own identity, entry rules, mission set, and analytics. The Club management module lets brands create, configure, and manage multiple clubs simultaneously — each targeting a different audience segment, goal, or product line. The live preview during creation ensures brands see exactly what ambassadors will see before publishing.

Status management (Active, Paused, Draft, Archived) lets brands season campaigns seasonally without losing historical data. Pausing a club freezes missions without deleting ambassador progress.

Mission Builder

Behavior Engine

The Mission Builder reduced average creation time from 23 minutes to 8 minutes by guiding admins through a structured 6-step wizard. Live preview, type-specific fields, and inline best-practice hints eliminate guesswork. Brands configure exactly what behavior they want, with coin rewards that reflect the effort required.

Analytics Dashboard

Insight Engine

Campaign performance is displayed across three levels: top-level KPIs, club-level breakdown, and mission-level funnels. Contextual insight cards surface when the system detects anomalies — always linked to a specific action. Export to CSV or PDF for stakeholder reporting. Time range filters and cohort segmentation allow brands to analyze specific user groups without leaving the dashboard.

User Segmentation

Ambassador Intelligence

The Members module gives brands actionable visibility into their ambassador base. Filter and search across multiple dimensions simultaneously. User profiles surface the full activity timeline, club memberships, and performance history. Tags let brands create custom segments (VIP, At-Risk, Product Tester) that persist across analytics filters and notification campaigns.

Rewards Configuration

Incentive Design

Brands configure the full reward stack: coin earn rates per mission, level-based multipliers, and what coins can be redeemed for (cash-back, gift cards, branded perks). Budget controls let brands cap total coin distribution per campaign to manage cost. The projected spend estimate in the Mission Builder ensures brands make reward decisions with cost context — not in the dark.

07 / Deep Dive: Mission Builder

The feature that determines campaign quality — and brand satisfaction

The Mission Builder is the highest-frequency and highest-stakes action in the dashboard. A well-built mission drives engagement and completion. A poorly configured one generates support tickets, confused ambassadors, and wasted reward budget. Getting this right was the central UX challenge of the entire product.

Problem

Admins were making consequential decisions without context.

Early versions of the mission form were a flat list of fields: name, description, reward, proof type, end date. No guidance. No previews. No indication of what "good" looked like. Admins filled in the form based on intuition — which meant wildly inconsistent missions with unpredictable performance.

The result: our top 5 support ticket categories were all mission-related. "Ambassadors are confused about what proof to submit." "My mission has 0 completions." "I set the wrong coin value — can you change it?" These weren't user errors — they were UX failures.

Insight

Admins don't need more fields. They need scaffolding — a structure that reduces the cognitive load of making 15 interdependent decisions in sequence.

Derived from 6 usability sessions with brand admins, session recordings, and support ticket analysis — July 2023

The problem wasn't the form fields themselves — it was how they were presented. Admins were being asked to make reward decisions before they'd defined requirements, and availability decisions before they'd built the mission content. The sequence was wrong, and there was no feedback between decisions.

Exploration

Three directions tested in prototyping

Option A — Modal wizard: Multi-step modal with 4 steps. Tested well for simplicity but felt constraining for complex missions. Admins wanted to go back and adjust earlier decisions after seeing later ones — the modal's linear flow made that awkward.

Option B — Single long form: All fields on one scrollable page. Admins liked the overview but felt overwhelmed. No clear sense of progress. High cognitive load when first encountering the form.

Option C — Horizontal stepper + live preview: Side-by-side: structured steps on left, live app preview on right. Admins could see consequences of their decisions as they made them. Went back and forth between steps naturally. Highest task completion and lowest error rate in testing.

Solution

A guided wizard with live consequences

The final Mission Builder uses a horizontal stepper (6 steps) with persistent live preview. Every field change updates the app preview card in real time — admins see exactly what ambassadors will see, before publishing. Best-practice tooltips are contextual, not instructional: shown on hover when a field is filled in suboptimally.

Critically, the sequence was redesigned: Type → Content → Requirements → Reward → Availability → Review. You define what the mission is before you decide what it's worth. Reward configuration shows type-appropriate coin ranges, so admins make calibrated decisions — not guesses.

Design Evolution

The Mission Builder went through 8 iterations. The key inflection points were: adding live preview (Round 3), restructuring the step sequence (Round 5), and adding contextual best-practice hints (Round 7).

V1 — Flat Form
Flat field list. No guidance, no preview, no step structure. High error rate in usability testing.
V2 — Stepped Wizard
Introduced stepper. Better progress visibility. Still no preview. Sequence still suboptimal.
V3 — Preview + Hints (Shipped)
Live preview added. Sequence restructured. Contextual hints. 65% reduction in mission-related support tickets.

09 / Key Design Decisions

The choices that shaped the product

Each decision emerged from a specific admin pain point or business constraint. Each one involved real trade-offs.

Decision 01
Problem

Admins creating missions had no idea if their coin reward values were appropriate — they were setting random amounts with no calibration to expected effort or platform norms.

Options Considered
  1. Free text input — admin sets any number
  2. Fixed coin values per mission type
  3. Slider with recommended range + free override
Decision

Slider with a highlighted "recommended range" band based on mission type, plus a manual input field to override if needed.

Why: Fixed values are too restrictive — brands have different economics and ambassador expectations. Free input is too unconstrained — it produces miscalibrated rewards that hurt mission performance. The slider with a nudge zone preserves flexibility while anchoring decisions to real platform data. Mission-related support tickets dropped 41% after this change.

Decision 02
Problem

Analytics data refreshed every 4 hours — an infrastructure constraint, not a design choice. But showing stale data without context caused admins to make incorrect optimization decisions based on outdated numbers.

Options Considered
  1. Show data as-is, no refresh indicator
  2. Show "as of [timestamp]" on every chart
  3. Persistent refresh banner with countdown + timestamp on all data points
Decision

A persistent, non-intrusive "Last updated: X ago / Next refresh in Y" banner in the analytics header, plus a subtle timestamp on each chart.

Why: Data without context of freshness is a trust problem. An admin who doesn't know data is 3 hours old may interpret a flat chart as "nothing's happening" when actually 2 hours of activity hasn't been captured yet. Surfacing the refresh cycle explicitly sets expectations and prevents false optimization decisions. It also communicates technical honesty — which builds long-term brand trust in the product.

Decision 03
Problem

The analytics section surfaced data — but not direction. Admins could see that a mission had a 18% completion rate, but had no guidance on whether that was bad, why it was happening, or what to do next.

Options Considered
  1. Raw data only — admins interpret themselves
  2. Static benchmarks ("18% is below the 30% average")
  3. Contextual insight cards with pattern-matched suggestions
Decision

Contextual insight cards that surface specific, actionable suggestions based on detected drop-off patterns — always linked to a CTA that takes the admin directly to the relevant edit flow.

Why: Benchmarks tell you you're below average — they don't tell you why or what to do. By mapping drop-off patterns to known causes (proof complexity → submission drop-off; low coin value → low start rate), we could surface relevant suggestions without ML or extensive data science investment. It made admins feel guided, not just informed. Campaigns that received at least one insight interaction saw 34% higher subsequent completion rates.

Decision 04
Problem

When editing a live mission, admins didn't know which ambassadors would be affected — would changes apply retroactively? Would in-progress submissions be impacted? The ambiguity caused admins to avoid editing live missions entirely, leaving underperforming missions running unchanged.

Options Considered
  1. Block edits on live missions — require duplicating to change
  2. Allow edits silently, no state communicated
  3. Allow edits with explicit scope confirmation ("Changes apply to: new starts only")
Decision

Allow edits on live missions with a persistent edit scope banner: "Changes apply to ambassadors who have not yet started this mission. In-progress submissions are not affected."

Why: Blocking edits means underperforming campaigns can't be fixed — hurting brands and reducing platform value. Allowing silent edits creates uncertainty and potential trust issues. Making the edit scope explicit removes ambiguity. Admins need to know the boundary of their action before taking it — especially in a live system affecting real users. This change reduced "I accidentally broke my mission" support tickets to zero.

11 / Challenges

What made this hard — and how we worked through it

01

Balancing flexibility with simplicity in the Mission Builder

Brands wanted total control — custom proof types, complex eligibility rules, multi-step requirements. But every additional configuration option made the builder harder to learn and more error-prone. We resolved this by separating "common configuration" (in the wizard) from "advanced settings" (in a collapsible section) — common paths are fast, complex cases are accessible but not ambient. 95% of missions use only the wizard-level settings.

02

Designing meaningful analytics without real-time data

Our 4-hour analytics refresh cycle was a hard constraint. The risk: admins would trust stale data, make bad decisions, and blame the product. We solved this through three strategies: explicit data freshness timestamps, contextual insight cards that are based on the last confirmed refresh (not interpolated), and a "pending completions" counter that shows activity since the last refresh in real time. Admins always know what they can and can't trust.

03

Handling the complexity of multi-club brand accounts

Brands managing 10+ clubs had serious navigation and context-switching problems. The sidebar's flat list approach broke down at scale — admins lost track of which club they were editing. We introduced a persistent "active club" context bar at the top of all pages, a quick-switch dropdown, and a global search that scoped results by club. Large accounts now switch context 3× faster than before.

04

Making the UX flows work without real-time validation feedback

Missions submitted for manual review could take hours — sometimes days — before being approved or rejected. Ambassadors needed to know their submission was received; brands needed visibility into a pending queue. We built a three-state pending system: Submitted → Under Review → Decided, with admin-facing queue management and configurable expected review time that was surfaced to ambassadors in the app. This eliminated "did my submission go through?" support tickets entirely.

12 / Reflection

What I learned, what I'd change

What I learned

  • Admin UX has different stakes than consumer UX. Consumer mistakes are personal and low-cost. Admin mistakes affect hundreds or thousands of downstream users. The threshold for "good enough" is higher — every decision needs to communicate its scope and consequences clearly.
  • Data without direction is noise. Surfacing raw numbers in the analytics layer made admins feel informed but paralyzed. The insight cards — simple pattern-matching driving actionable suggestions — had more impact on campaign performance than any chart we built. The lesson: always ask "what should the admin do with this data?"
  • Sequence matters as much as fields. The Mission Builder's biggest improvement wasn't adding features — it was reordering the steps so decisions were made in logical dependency order. Defining what a mission is before deciding what it's worth produced better missions with less cognitive effort.
  • Constraints force honest design. The 4-hour refresh cycle forced us to be explicit about data freshness rather than hiding it. Being honest about limitations built more admin trust than a polished UI that masked the constraint would have.
  • The admin experience is the product's lever. Every design decision in the dashboard directly determines the quality of ambassador experiences across the entire platform. Investing in admin UX isn't overhead — it's leverage.

What I'd improve

  • Mission templates. High-performing brands developed reusable mission patterns — "social share", "monthly purchase", "referral burst" — but had to recreate them from scratch every time. A template library would dramatically reduce creation time for experienced brands while also educating new ones on effective patterns.
  • Better onboarding for new brands. The first-session experience was too open-ended. Brands were dropped into an empty dashboard without enough guidance on "what should I create first?" A structured onboarding flow with step-by-step guidance for the first club + first mission would reduce the time-to-first-live-campaign from ~3 days to same day.
  • Collaborative editing. Many brands have 2–3 team members working in the dashboard simultaneously. We built no awareness of concurrent editing — two admins could overwrite each other's changes silently. Real-time presence indicators and edit locking for in-progress missions would prevent data conflicts and the confusion they cause.
  • Richer segmentation in analytics. The current filtering is useful but surface-level. Cohort analysis — "show me the performance of ambassadors who joined in January vs. March" — requires export to external tools. Building this natively would unlock retention modeling directly inside the dashboard, which is the next strategic priority.

The most important design lesson from Club Dashboard: a great SaaS product doesn't just give admins tools — it gives them judgment. Every dashboard feature should make the admin more capable, not just more efficient. When we got that right — when the insight cards told admins what to do, when the mission builder nudged them toward better decisions, when the analytics made optimization feel obvious — brands built better campaigns, ambassadors had better experiences, and the platform grew. That's the standard I'd hold any admin product to.
