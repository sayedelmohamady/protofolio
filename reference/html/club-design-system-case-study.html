00 / Intro

What is the TIE design system?

TIE (Club’s design system) is the single source of truth for UI across the ambassador platform — tokens, components, and patterns shared between Flutter and React. It aligns teams on one visual and interaction language so Club scales without fragmenting the brand.

01 / The Challenge

Why the design
system needed to exist

Club connects brands with ambassadors to run marketing missions — across a Flutter mobile app and a React web platform. As the product scaled, design and development needed a shared language to stay cohesive.

Inconsistency at scale

UI patterns duplicated across both platforms — fragmented brand experience.

Friction between design and dev

Slow handoffs and ambiguous specs led to rework and misaligned components.

No unified brand design language

Club lacked a cohesive visual identity across the ambassador app and brand platform.

Unsustainable design velocity

Every feature designed from scratch — no tokens, no docs, no shared primitives.

05 / Governance

Design meets code:
Storybook & Widgetbook

A design system only works if it's trusted by the people building with it. Governance means the system is documented, tested, and maintained — not just designed.

Storybook
React Web Platform

Living documentation for all React components on the brand management platform. Each component is catalogued with all its variants, states, and props — giving developers a reliable reference and a visual test suite.

  • Component stories for all interactive states
  • Visual regression testing baseline
  • Accessible component documentation
  • Isolated development environment
  • Single source of truth for frontend engineers
Widgetbook
Flutter Mobile App

The same governance layer for the Flutter app. Each widget is catalogued, documented, and testable in isolation — closing the loop between what's designed in Figma and what's shipped in the ambassador app.

  • Widget catalogue for all Flutter components
  • Device and theme preview testing
  • Hot-reload documentation workflow
  • Direct collaboration with Flutter engineers
  • Design-to-code consistency verification

05b / Vibe Coding

Designing in code

One of my most distinctive contributions was participating directly in the development of design system components through a practice I call "vibe coding" — a fluid, collaborative loop between design intent and code output.

Design the component in Figma

Each component starts in Figma with all variants, states, and token references clearly defined — giving engineers a precise specification before a single line of code is written.

Sit alongside the engineer

Rather than throwing specs over a wall, I work directly with the engineer as they build — providing real-time design feedback and catching deviations early, before they become habits.

Contribute code directly

Where possible, I write or adjust code myself — tweaking spacing values, token references, border radii, and animation curves directly in the codebase to match the design intent precisely.

Validate in Storybook or Widgetbook

The finished component is verified against the Figma spec in the documentation environment — checking all states, themes, and responsive behaviour before it's added to the library.

Document and publish

Once validated, the component is documented in both Figma and the code documentation tool — ready to be used, extended, and governed by the full team.

07 / Process Deep-Dive

How we built it:
phase by phase

The Club TIE system wasn't designed all at once. It evolved through deliberate phases — from discovery and audit through to active governance — with each phase building on a validated foundation.

Phase 01

Audit & discovery

Before designing anything new, we mapped what already existed — cataloguing UI patterns, inconsistencies, and reuse opportunities across both platforms.

  • Screenshotted and inventoried all existing UI across app and web
  • Identified duplicated patterns and divergent component states
  • Interviewed engineers on the biggest friction points in handoff
  • Benchmarked competitor design systems for structural reference
  • Defined the scope: what would and wouldn't be in v1
Phase 02

Foundations first

With audit findings in hand, we established the primitive layer — tokens, typography, colour, and spacing — before touching a single component. No building on sand.

  • Defined the full colour token system: primitive → semantic → component
  • Built the typography scale in Figma and mapped it to Flutter text themes
  • Established the 8px spacing grid and component shape language
  • Created the Primitives and Foundations Figma libraries
  • Synced token values with the engineering team for alignment
Phase 03

Core component build

With solid foundations, we systematically built the core component library — starting with the highest-frequency, highest-impact UI elements.

  • Prioritised components by usage frequency across both platforms
  • Built each component with all variants, states, and interactive props
  • Documented component anatomy, usage guidelines, and do/don'ts
  • Ran vibe coding sessions with engineers to ship in parallel
  • Published core components to Storybook and Widgetbook progressively
Phase 04

Platform specialisation

Once the shared core was stable, we extended it into platform-specific layers — App Components for Flutter, Platform Components for React — each inheriting from the same foundation.

  • Defined which components diverge by platform vs which stay shared
  • Built App Components tuned to Flutter's interaction model
  • Built Platform Components for React's desktop-first paradigms
  • Maintained token linkage so platform variants stayed in sync
  • Added mission-specific and ambassador-specific composed components
Phase 05

Icons & graphics

Clubicons and the Club Graphics library were built as dedicated systems — giving the product a distinctive visual voice beyond just UI components.

  • Defined icon grid, stroke weight, and optical correction rules
  • Designed Clubicons set across navigation, action, status, and social
  • Exported icons as optimised SVGs for Flutter and React
  • Built the Club Graphics illustration library with a consistent art style
  • Documented usage guidelines for icons and graphic assets
Phase 06

Patterns, templates & governance

The final phase turned the component library into a living system — adding design patterns, app templates, and the governance tooling to keep it healthy over time.

  • Documented repeatable design patterns for common UX problems
  • Created app templates for core screens and user flows
  • Established Storybook and Widgetbook as the governance layer
  • Defined contribution guidelines for adding new components
  • Set up a regular design system review cadence with the team

Design-first, then code

Every component was designed in Figma with full spec coverage before any code was written — reducing back-and-forth during development.

Parallel shipping

Vibe coding sessions meant design and code progressed in parallel — components landed in both Figma and production faster than sequential handoff.

Foundations as a forcing function

Building primitives and foundations first made every subsequent decision easier — tokens meant design choices propagated automatically across the system.

Progressive documentation

Rather than documenting everything at the end, each component was documented as it was built — making the system usable from day one of each phase.

09 / Learnings

What I'd tell myself
at the start

Building a design system from the ground up across two platforms is one of the most complex design challenges I've faced. Here's what I learned — and what I'd do differently.

01

Foundations are worth the investment — every time

It's tempting to skip straight to components. But every hour spent on a solid token and primitive layer saves ten hours of rework later. The more thorough the foundations, the faster everything built on top of them moves.

02

Governance is a product, not a meeting

A design system without governance is just a Figma file. Storybook and Widgetbook transformed the system from a design artefact into a living product — one that could be trusted, tested, and extended by the full team.

03

Vibe coding changes the relationship

The most impactful thing I did wasn't designing components — it was sitting with engineers and helping ship them. Being present in the codebase earned trust, caught issues early, and made the final result far more faithful to the design intent.

04

Scope ruthlessly in v1

The instinct is to design everything up front. But a focused, well-executed v1 — even if it doesn't cover every edge case — gets adopted faster and builds more momentum than a sprawling system that never ships.

05

Multi-platform is a multiplier — of both value and complexity

Serving Flutter and React from the same foundation amplified the system's value significantly. But it also meant every decision needed to work in two different paradigms. Thinking in tokens rather than platform-specific values was the key to making it sustainable.

06

A design system is never done

The most important mindset shift was accepting that Club TIE is a living product — not a project with an end date. Continuous iteration, regular reviews, and a clear contribution process are what keep a system healthy over time.

What's next for Club TIE

Roadmap & future improvements
  • Formalise the token pipeline with a dedicated token export tool (e.g. Token Studio) to automate sync between Figma and both codebases
  • Expand the Clubicons set to cover more mission types, social platforms, and product-specific concepts
  • Build out a dedicated design system documentation site — going beyond Storybook/Widgetbook to a public-facing reference
  • Add accessibility audit checkpoints to the component governance process — automated a11y testing in CI
  • Extend the illustration system into a full motion library — defining animation patterns for the Flutter app
  • Introduce a contribution framework that allows product squads to propose and ship new components without bottlenecking through one person
