00 / Intro

What is the TIE design system?

TIE (Club’s design system) is the single source of truth for UI across the ambassador platform — tokens, components, and patterns shared between Flutter and React. It aligns teams on one visual and interaction language so Club scales without fragmenting the brand.

07 / Process Deep-Dive

How we built it:
phase by phase

The Club TIE system wasn't designed all at once. It evolved through deliberate phases — from discovery and audit through to active governance — with each phase building on a validated foundation.

Phase 01

Audit & discovery

  • Inventoried all existing UI across app and web
  • Identified duplicated patterns and divergent states
  • Defined the v1 scope with engineering input
Phase 02

Foundations first

  • Colour tokens: primitive → semantic → component
  • Typography scale mapped to Flutter text themes
  • 8px spacing grid and shape language established
Phase 03

Core component build

  • Prioritised by usage frequency across both platforms
  • All variants, states, and interactive props covered
  • Vibe coded with engineers to ship in parallel
Phase 04

Platform specialisation

  • Forked into Flutter App Components and React Platform Components
  • Shared token linkage kept platform variants in sync
  • Added mission- and ambassador-specific composed components
Phase 05

Icons & graphics

  • Clubicons across navigation, action, status, and social
  • Exported as optimised SVGs for Flutter and React
  • Club Graphics illustration library with a consistent art style
Phase 06

Patterns, templates & governance

  • Repeatable design patterns for common UX problems
  • App templates for core screens and user flows
  • Storybook and Widgetbook as the governance layer

05b / Vibe Coding

Designing in code

A fluid loop between design intent and code output — I participate directly in building components, not just speccing them.

Design the component in Figma

Variants, states, and token references defined upfront — a precise spec before any code is written.

Sit alongside the engineer

I work directly with the engineer as they build — giving real-time feedback and catching deviations before they become habits.

Contribute code directly

I tweak spacing, token references, and animation curves in the codebase myself to match design intent precisely.

Validate in Storybook or Widgetbook

Verified against the Figma spec — all states, themes, and responsive behaviour checked before it's added to the library.

Document and publish

Documented in Figma and the code tool — ready to be used, extended, and governed by the full team.

09 / Learnings

What I'd tell myself
at the start

Six things that shaped how I think about design systems.

01

Foundations save 10× the time

Every hour on tokens prevents ten hours of rework later.

02

Governance is a product, not a meeting

Without Storybook and Widgetbook, the system is just a Figma file.

03

Vibe coding changes the relationship

Being in the codebase earns trust and catches drift early.

04

Scope ruthlessly in v1

A focused v1 ships and gets adopted. A sprawling one never lands.

05

Multi-platform multiplies value and complexity

Tokens — not platform values — are what make it sustainable.

06

A design system is never done

Treat it as a living product. Regular reviews keep it healthy.
